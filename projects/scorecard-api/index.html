← Past

Automated testing, manual everything else

A standard thermal test drives a grill through a set-point staircase while a data acquisition system logs the temperatures. That part ran itself. What did not run itself was everything after the last data point.

The analysis existed and it was good — a Shiny application that scored a test and produced the plots the team used. It just needed a person: transfer the files off the acquisition laptop, open the interface, type in the model, the firmware version, the trial number, the test number, wait for the result, screenshot it, attach it to the ticket, write the summary.

Three minutes, give or take. Which sounds like nothing until you notice that standard practice is three grills running three tests each, and every one of those needs the same three minutes of somebody's attention — including the waiting.

● Present

An endpoint the rig can call by itself

The insight is small and slightly annoying in hindsight: the sequencer that runs the test already holds every piece of metadata the analysis was asking a human to retype.

01

Where the three minutes went

None of these steps is hard. Every one of them is a person doing something a machine already knows. The typing is the worst of it — model, firmware, trial number, test number, four chances to introduce a typo into a file name that someone will search for later.

02

Three grills, three tests

Multiply it by the standard practice and the session costs about half an hour. The API path costs one upload at the end, because the analysis has already happened for every grill by the time anyone looks. That is the 83%.

03

What was already there

Thermocouples on the grate, the controller's own log, and a sequencer driving the whole profile. Two CSV files fall out at the end of every test. This half of the system was never the problem.

04

One request at the end of the test

The sequencer runs a batch script when a test completes. That script sends both CSVs and the test metadata to an R Plumber API running in a Docker container on a Linux server. No interface, no typing, no transfer.

05

Three outputs, ready to attach

A scored plot as an image, the graded results table as an image, and an interactive plotly page for anyone who wants to zoom in on a specific event. The same analysis code the Shiny app used — that was a hard requirement, because two copies of an analysis is two analyses.

06

What the scorecard scores

The test walks the controller up a staircase of set points and holds at each one long enough to reach steady state. That commanded profile is the dashed line — the thing every measurement is judged against.

07

Two channels that disagree on purpose

The controller probe sits near the fire and reads hot. The grate thermocouple sits where the food is, and it is the one the controller is actually tuned against. The gap between them is not an error — it is the number a cook cares about versus the number the grill thinks it is holding.

08

Every step has the same signature

Command a step up, and the controller overshoots, then settles into a slow sawtooth as the auger cycles pellets in. The scorecard ignores the ramp entirely and measures the second half of each dwell, where the behaviour is steady enough to mean something.

09

A grade per set point

Two numbers per step: how far the settled grate temperature sits from target, and how tightly it holds. The tolerance scales with the set point, because holding ±10°F at 500 is a much harder ask than at 225. On this unit the grades fall off at the top of the range — which is the finding, and exactly the kind of thing that used to depend on whoever was reading the plot that afternoon.

The parts that fought back

Development took a month, and most of it was not the analysis. A representative sample, because the polished version of this story is less useful than the real one:

  • Docker could not write to the host disk. Days of bind-mount and --mount syntax, no errors, no file. I stopped fighting it and changed the design instead: return the results in the HTTP response rather than saving them somewhere and telling the user where to look. That turned out to be the better architecture — the endpoint became stateless, which is why it has needed no maintenance since.
  • PhantomJS. Rendering a styled table to an image needs a headless browser, and the standard R package wants PhantomJS, which will not install cleanly in the container. Two days lost before switching to webshot2, which uses headless Chrome instead. Immediate fix.
  • Error 137. The plotly output died with a pandoc failure that turned out to be the OOM killer — the container's memory ceiling was too low for document conversion. Raise the allowance, done.
  • Persistence. A container running in a terminal dies with the terminal. systemd made it a service that survives reboots and comes back on its own.

None of that is glamorous, and all of it is the difference between a proof of concept and something the team still uses. I logged every one of these in the ticket as it happened, partly for the next person and partly because the dead ends are the part I would want to read.

→ Future

One endpoint per repetitive analysis

The thermal scorecard is one test. The pattern underneath it — instrumented rig, HTTP request, analysis as a service — has nothing to do with thermal testing at all.

Everything the lab does looks like this: a rig produces files, a person runs a known analysis over them, and a result gets attached to a ticket. Each of those is an endpoint waiting to be written, and the second one is much cheaper than the first because the container, the hosting and the request pattern already exist.

The bigger prize is what happens when results stop being attachments. Right now every test produces images that live on a ticket, which means the fleet of tests we have run is not queryable. Writing results to a database instead would turn three years of thermal tests into a dataset: how does this model compare to its predecessor at 500°F, has controller behaviour drifted across firmware versions, which units were outliers and did they stay that way. That is a different class of question than any single scorecard can answer, and the API is the thing that makes it possible — every test that runs is already an insert waiting for a table.

The general version of the rule, which I would apply anywhere: if a team does the same analysis by hand more than once a week, that analysis wants to be an endpoint. The cost is a container and an afternoon. The return is every hour after that, plus a dataset you did not have before.
